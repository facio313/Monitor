# 이메일 알림 과다 발송 수정 — 2026-09-13

## 확인한 문제

18:00–23:09 KST의 발송 기록은 운영 70통, 시험 2통이었다. 모두 첫 번째
전송 시도에 성공했다. 운영 메일 중 TCP가 33통이었고, 전체 복구 안내는
30통, 정기 보고서는 6통이었다. 따라서 SMTP 재시도보다 탐지·알림 정책이
주요 원인이었다.

TCP는 한 구간의 비율만 사용했다. 예를 들어 6/60 세그먼트가 10% 위험으로
바로 승격됐다. HTTP 지연은 즉시 신호와 지속 규칙이 각각 메일을 보냈으며,
지속 규칙이 동일한 5분 주기 검사 결과를 매분 새로운 관측으로 세었다.

## 적용 정책

- TCP 메일: 최근 최대 5분의 실제 카운터 차이를 합산한다. 최소 3개 관측
  구간, 관측 종료 시각 간 120초, 송신 1,000개 또는 재전송 20개를 요구한다.
  이 조건에서 가중 비율 1%/5%를 주의/위험으로 판단한다. 저트래픽에서도
  지속적인 재전송은 절대 건수 조건으로 알릴 수 있다. 최초 기준 표본은
  구간 횟수에 포함하지 않는다.
- 짧은 자원 경고: 서로 다른 관측 3회·120초가 필요하다. 위험 승격은
  위험 관측 2회·60초가 필요하다. 주의/위험을 오가는 동안에도 주의 이상
  상태의 지속성은 보존한다.
- HTTP 지연: 원본 검사 시각이 다른 성공한 검사 2회·240초가 필요하다.
  복구도 실제 정상 검사 2회를 요구한다. 밀리초가 있는 원본 시각을
  보존하여 같은 결과를 다시 읽어도 횟수가 늘지 않는다.
- SMTP 중복 경로: `monitor-hourly-and-incidents` 경로의 `excludeRuleIds`에
  `TcpRetransmissionHigh`, `HttpLatencyHigh`만 추가했다. 해당 메일은 위의
  추가 신호 경로가 담당한다. 기존 규칙의 로컬 기록과 다른 경로는 유지한다.
- 동일 주의 재발: 15분 동안 재발 메일을 제한하며, 새로운 위험 승격은
  통과시킨다. 가용성 실패·OOM·현재 전원 이상 같은 명확한 위험은 즉시 알린다.
- 작은 HTTP 표본: 느린 요청 비율은 전체 20건·느린 요청 3건 이상에서
  적용한다. 최대 지연 5초/15초의 절대 기준은 유지한다. 5xx 비율에 따른
  위험 판정도 최소 요청·오류 건수를 요구한다.
- SSH: 단일 거부는 로컬 관측에 남긴다. 즉시 메일은 5분간 5건부터이며,
  기존 20건 위험 기준은 유지한다. 정기 보고 주기는 매시간 그대로이다.

재부팅, 누락, 오래된 자료, 뒤늦게 도착한 자료는 정상 관측을 만들어내지
않는다. 메일로 통지하지 않은 짧은 사건은 복구 메일도 보내지 않는다.
대기열에 들어간 뒤 밀려난 복구 알림은 원래 ID로 재등록하며, 완료된
발송 기록을 복원하거나 다시 보내지 않는다.

## 검증

Python 전체 테스트 638개 실행: 성공, 환경 조건에 따른 1개 건너뜀.
이후 추가된 독립 회귀 4개도 성공했다. 원본 시각의 밀리초 처리 보완 후
알림 생산자·독립 회귀 테스트 26개를 다시 실행하여 모두 성공했다.

18:00–23:09 KST의 호스트 이력과 네트워크 진단 291개를 격리된 임시
대기열로 재생했다. SMTP·네트워크·비밀정보 읽기는 차단했고 발송 시도는
0회였다. 291회 모두 생산자 상태가 `ok`였다.

| 비교 가능한 항목 | 과거 발송 | 새 로직의 재생 결과 |
| --- | ---: | ---: |
| TCP | 33통 | 6통: 주의 3, 복구 3 |
| 합성 HTTP 지연 | 즉시/지속 경로 합계 4통 | 2통: 주의 1, 복구 1 |

실제 정상 HTTP 검사 시각은 23:02:04.357, 23:07:06.726 KST였다. 새 로직의
복구는 두 번째 검사를 수집한 23:07:09이며, 첫 검사 결과를 두 번 읽은
23:04:01에 복구하지 않는다.

과거 SSH·기존 규칙 상태·HTTP 요청 집계·컨테이너·저장장치·재부팅 상태는
재생하지 않았다. 따라서 운영 70통 전체가 특정 개수로 줄어든다고
단정하지 않는다. 상세 재생 결과는
`/tmp/monitor-notification-replay-fixed.6hni5r/summary.json`에 남겼다.

## 운영 적용

23:41 KST에 수집·발송 타이머를 재개했다. 두 타이머만 일시 중지하고,
이미 실행 중인 작업이 끝난 뒤 아래 6개 모듈과 Gmail 경로만 교체했다.

`alert_engine.py`, `alert_runtime.py`, `alert_store.py`, `alert_delivery.py`,
`security_signals.py`, `notification_reports.py`.

기존 데이터베이스, 발송 이력, 비밀번호, 수신자, 정기 보고 슬롯은 유지했다.
적용 전 코드와 설정은 루트 전용
`/var/backups/monitor-notification-noise-20260913.bQ4fnp/before`에 보관했다.
백업에 전체 서비스·컨테이너·호스트 데이터 스냅샷은 포함하지 않았다.

23:45 KST 운영 확인에서는 수집·발송 타이머가 모두 활성 상태였고,
수집기와 발송 작업이 성공 종료했다. 최신 생산자/규칙 평가 상태는 `ok`,
4개 입력 출처는 모두 `fresh`였다. TCP는 실제 3개 구간·190초를 모아
41/13,372 = 0.307%로 정상 판정했다. 발송 완료 운영 75통은 적용 직전과
동일했고, 대기·재시도·실패는 모두 0이었다. 정기 보고 슬롯도 보존됐다.

배포 후 실제 검사 시각인 23:42:45가 비공개 규칙 상태에 저장됐으며,
23:44:34까지 수집기가 평가를 반복해도 해당 원본 시각은 바뀌지 않았다.
공개 규칙 상태는 기존 19개 필드를 유지해 클라이언트 계약에 새 비공개
체크포인트가 노출되지 않았다. 설치한 6개 모듈은 저장소와 바이트 단위로
일치했고, 적용 후 수집 로그에 예외나 마이그레이션 오류는 없었다.

롤백 시에는 두 타이머와 실행 중인 작업을 정리하고 코드와 경로 설정을
같이 되돌려야 한다. 이전 규칙 상태 판독기는 새 `lastSampledAt` 필드를
모르므로, 되돌릴 경우 최신 비공개 규칙 상태에서 이 필드만 제거하는
호환 변환이 필요하다. 과거 SQLite나 규칙 상태 전체를 복원하면 이미
발송한 사건을 재생할 수 있으므로 사용하지 않는다.
