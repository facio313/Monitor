# TCP 재전송 표시 진단 — 2026-09-13

19:56:42 KST 관측에서 TCP 재전송은 6/4,787세그먼트(0.125%)였으며 HTTP 검사는 200, 479ms였다. 계속되는 장애보다 **송신량이 작은 1분 구간에 최소 표본량 조건 없이 비율만 적용하는 즉시 위험 판정**이 반복되는 상황이다. 개별 재전송의 상대·서비스·물리적 원인은 호스트 집계만으로 특정하지 못했다.

새 상세 이력의 보관 시작은 17:10:35 KST로, 요청한 최근 6시간 전체를 설명하지는 못한다. 17:11–19:56의 유효 157표본에서 재전송 합계는 617/331,747(가중 0.186%), 5% 이상은 5회이며 모두 연속되지 않은 단일 표본이었다.

추가 확인한 유효 159표본 모두 저장된 분자·분모를 재계산한 값과 일치했다. 누적 카운터를 구간 값으로 잘못 사용하거나 송신 델타를 누락한 증거는 없다. 송신 1,000세그먼트 이상인 60표본에서는 최고 1.541%였고, 위험 5회는 모두 그보다 적은 송신량에서 발생했다.

`linux_telemetry.collect_tcp`는 이전 수집과의 `RetransSegs` 및 `OutSegs` 차이로 비율을 계산한다. UI와 추가 즉시 알림은 1%부터 주의, 5%부터 위험이며 최소 송신량 조건은 없다. 별도의 `TcpRetransmissionHigh` 규칙은 5회·4분 지속 조건이 있어, 확인한 최근 6시간 규칙 전이 기록에는 새 TCP 발생·해소 전이가 없었다.

공개 알림 기록의 TCP 9사건은 확인 시 모두 해소였다. 마지막 사건은 19:42:51–19:54:34 KST였다. 정상 표본 사이에 다시 1% 이상 표본이 나타나면 해소 확인 횟수가 초기화되므로, 서로 다른 정상 표본 2회가 이어질 때까지 사건이 유지된다. 동일 사건의 무조건 반복 전송이 아닌 새 사건·위험 승격·해소의 반복 구조이다. 개별 메일 성공 횟수는 비공개 발송 큐를 조회하지 않아 단정하지 않았다.

연관 증거:

- 같은 기간 고유 HTTP 검사 33개 모두 성공, 347–603ms. 위험 표본과 함께 확인한 CPU는 약 18%, 메모리 PSI는 0이었다.
- 이력의 인터페이스 RX/TX 오류는 모두 0. RX 드롭은 0.09–0.11/초로 일정했다.
- 물리 `eth0`는 UP, RX/TX 오류·TX 드롭·충돌은 0. 누적 RX 드롭만으로 TCP 손실 원인을 특정할 수 없다.
- 짧은 추가 수동 집계 관측에서 재전송 4개 증가 중 SYN 재전송 카운터가 3개 증가했다. 일부 연결 수립 단계 재시도가 있다는 근거이며, SSH 공격이나 특정 서비스의 원인이라는 증거는 아니다.

[Linux 공식 SNMP 설명](https://docs.kernel.org/networking/snmp_counter.html)에 따르면 `TcpOutSegs`는 재전송을 제외하고 SYN·ACK·RST를 포함한다. 따라서 현재 비율을 그대로 실제 패킷 손실 확률로 해석해서는 안 된다. `TCPSynRetrans`는 SYN 및 SYN/ACK 재전송 집계다. [인터페이스 통계 설명](https://docs.kernel.org/networking/statistics.html)상 RX 드롭에는 지원하지 않는 프로토콜이나 수신 필터 관련 폐기도 포함될 수 있다.

TCP 진단 과정에서는 임계값·수집 설정·서비스를 변경하지 않았다. 능동 네트워크 부하, SMTP, 개별 연결·컨테이너 조사 및 제외된 서비스 접근도 하지 않았다. 별도로 요청된 SSH 출처 기록·화면 추가는 [SSH 관측 안내](ssh-access-observations.md)에 설명한다. 다음 개선을 선택한다면 원래 비율·분자·분모를 계속 보여주면서, 적은 송신량에 대한 표시와 지속 여부를 위험 판정에 함께 반영할 수 있다.
